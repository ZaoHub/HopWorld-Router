# HopWorld Router 版本发布与更新

## GitHub 稳定发布

`router/version.py` 声明源码版本，管理 API 和更新程序以此识别主版本。日常代码合并到 GitHub `main` 后运行 V1 检查。准备正式发布时，将声明改为目标版本并从 `main` 的对应提交推送匹配的标签，例如 `v1.0.1`。发布工作流验证标签与版本声明、提交归属和测试结果，然后构建 Debian 软件包、校验 SHA-256 并上传到 GitHub Releases。

安装端查找与当前主版本匹配的正式发布。预发布和草稿跳过，V1 稳定更新流程只选择 V1 发布。V2 可独立设置主版本、候选内核及迁移策略。跨主版本升级需要按当时的发布说明验证数据和兼容性。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)

## 控制台

- 「系统设置 → 系统维护」可配置程序的自动检查和自动安装，也可主动检查后手动安装。自动检查与执行在服务端运行。
- Debian 包安装使用「Router Debian 软件包」独立策略。采用 GitHub Releases 的官方包，核对 SHA-256、包名、版本和架构后交由 APT 安装。它仅选择 Router 本身的包和该包所需依赖。主机其他软件由服务器自己的包管理策略维护。
- 每个内核有自己的自动或手动策略。自动更新只处理已由 Router 安装到数据目录的内核。发布物通过 SHA-256 校验和服务器执行检查后才写入磁盘。运行中的实例会在下次重启时采用新版。当前加密 DNS 策略锁定的 sing-box 会阻止替换。
- 右上角的铃铛显示未读条数，打开后可查看发现、开始、完成和失败。记录保存在 Router SQLite 数据库，可显式标为已读。

Git 工作区和系统包是两种独立发布路径。标准 Git systemd 部署由服务器管理员从新源码安装或刷新更新服务，再用后台启用稳定更新。

```sh
sudo bash /opt/hopworld-router/deploy/hopworld-install-page-update.sh
```

Git 路径只允许干净的所有者受控工作树快进到同主版本的正式标签。更新前备份数据库，切换失败时尝试恢复原代码和虚拟环境。仅当正式发布中附带经校验的同主版本包，Debian 更新才会调用 APT。Docker、第三方发行包和手动解包目录继续由原有部署系统升级。升级源码依赖时先构建新虚拟环境再切换。

## V2 扩展

V1 管理权限仍为单管理员。更新模块用组件标识保存策略和事件，从现有内核清单读取更新项。新增内核时同步登记内核启动、平台资产选择和配置校验，再纳入发布验收。数据库包含独立的功能迁移记录，更新模块的初始迁移只新增策略和事件表并保留已有设置。若 V2 增加用户，届时按权限模型迁移通知读取位置，避免跨用户共用读取状态。
